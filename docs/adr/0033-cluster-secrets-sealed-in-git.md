# The cluster's Secrets live in Git, sealed to the cluster's controller

Each Secret the lab cluster reads is built from `.secrets/` (generated by `make secrets`, never in Git) and sealed against the Sealed Secrets controller's public certificate, which is committed (`deploy/sealed-secrets/cert.pem`, so sealing needs no cluster). It is written beside the manifests of the Application that deploys it:
- each cell's `shop-secrets`;
- the control plane's and the edge's secrets and per-cell credentials;
- Grafana's login and the alert webhook.

Only the controller's private key decrypts them. That key lives in `kube-system` and in a backup under `.secrets/` (`make seal-key-backup`); `make secrets` restores it into a cluster that has none, and `make seal-key-restore` restores it on demand.

Sealing is randomised, so each sealed file records an HMAC of its plaintext (keyed by a local key) and is re-sealed only when its values change. `make secrets` can then run any number of times without changing Git.

## Considered Options

- **Keep applying Secrets from the laptop** (`kubectl`, the state before Phase 7): rejected. A cluster could not be rebuilt from the repository and its key backup, and no change to a Secret went through review.
- **An external secret store** (Vault, a cloud KMS): rejected for the lab, a service to run and to unlock. Out of scope (Phase 7).

## Consequences

- The switch went through the controller's adoption of the existing Secrets (marked as managed) with their values unchanged, so no pod restarted. Pods still read a Secret at start: a change that adds a key needs its sealed file deployed first (dependencies first), and a restart.
- Losing both the cluster's key and its backup loses every Secret's value in Git. The restore was rehearsed (Phase 7 evidence): with the key gone nothing decrypts, and with the backup back everything did within 6 s.
- Gitleaks allows one shape only: a line that is one key's kubeseal ciphertext, in a sealed file under `deploy/`.
