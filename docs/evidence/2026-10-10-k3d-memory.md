# Memory on the lab cluster (tickets 08 and 09)

Measured 2026-10-10 on the author's workstation: Apple M2, 16 GB RAM; Colima VM with 6 CPUs and
10 GB (9.9 GiB usable); k3d 5.9.0 running one k3s v1.35.5 server. The Compose stack was stopped.

| State | k3d node container | Colima VM used | Colima VM available |
|---|---|---|---|
| Shop dev environment only (Postgres, Redis, 4 services, k3s system pods) | 970 MiB | 1,563 MiB | 8,358 MiB |
| + Argo CD (chart 10.10.2, app v3.5.4; no Dex, notifications, or ApplicationSets) | 1,662 MiB | 2,120 MiB | 7,801 MiB |
| + monitoring (kube-prometheus-stack 92.3.0, alert catcher; ticket 09) | 4,130 MiB | 4,052 MiB | 5,869 MiB |

Per-pod working sets at idle (metrics-server): storefront 46 MiB, worker 37 MiB, PostgreSQL
36 MiB, order-service 27 MiB, catalog-cart-api 27 MiB, Redis 6 MiB; Traefik 18 MiB, CoreDNS
13 MiB, metrics-server 20 MiB; Argo CD server 35 MiB, application controller 22 MiB.

With monitoring (ticket 09, measured after the stale-Pending alert drill): Grafana 415 MiB,
Prometheus 375 MiB (1-day retention, 1 GB cap), Alertmanager 40 MiB, Prometheus operator 23 MiB,
kube-state-metrics 19 MiB, alert catcher 10 MiB; 882 MiB for the monitoring namespace in total.
The shop namespace uses 216 MiB and Argo CD 435 MiB in total.

Conclusion: the POC's main feasibility risk (fitting the stack in 10 GB) is cleared with a wide
margin. With the monitoring stack added, about 5.7 GB is still available in the Colima VM. Resource requests for the
services (96-128 MiB) are 2-3x their idle use, leaving headroom for load; they should be
revisited with measurements under load.

Commands: `docker stats --no-stream k3d-shop-server-0`, `kubectl top pods -A`,
`colima ssh -- free -m`.
